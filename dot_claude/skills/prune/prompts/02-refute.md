## 調べる範囲

対象リポジトリの中と、上に挙げた外部境界まで。外部リポジトリ、本番環境、稼働中のデータなど、
ここから確かめられないものは「確かめられなかった」として扱い、断定しないこと。

候補には 2 種類あり、**問うことが違います**。候補リストにどちらか書いてあります。

## 種類 1「消す」(未参照・到達不能・役目を終えた・依存とビルド)

種類 1 には、**利用の有無で決まるもの**と、**決まらないもの**があります。先に見分けてください。

利用の有無で決まらないものは、現に読まれていても消せることがあります。問うことが違います。

| 候補 | 問うこと | 反証されるのは |
| --- | --- | --- |
| 到達不能な分岐 (B) | その分岐に到達する入力・状態・ビルド条件があるか。関数が使われていることは反証にならない | 到達する経路があったとき |
| 実態と違うコメント、ドキュメント | 現在の実装と一致するか。参照されているかは問わない | 一致していたとき |
| コメントアウトされたコード | 元に戻す予定が記録に残っているか (issue、コミット、コメント本文) | 予定が確認できたとき |
| 廃止された機能のテスト・フィクスチャ | その機能のプロダクトコードがまだ残っているか | 残っていたとき |
| 常に有効なフラグ、両対応の分岐 | 反対側の分岐に入る経路が今も残っているか | 残っていたとき |
| 互換シム、移行用コード | その互換経路を今も必要とする入力・呼び出し元・保存済みデータがあるか (無効化して壊れるものがあるか) | あったとき |
| 重複した設定 | 消すと最終的な設定値・優先順位・対応する環境が変わるか | 変わるとき |
| リポジトリに置かれた生成物 | 生成手順が残っているか | 生成手順が無く、再生成できないとき |

生成物については、反証できなかった場合も**判定を「判断保留」にし、補足に
「消すかどうかは依頼者の判断が要る」と書いてください**。

利用の有無で決まるもの (未参照、使われていない依存や CI ジョブ) は、以下のとおり。

**まだ使われている証拠を探してください。** 1 件でも見つかれば、その候補は消せません。
静的な呼び出しが無いことは、使われていないことを意味しません。次を当たってください
(その候補に当てはまらない項目は飛ばしてよい。**当たった項目だけを報告に書く**)。

1. **名前による動的参照** — リフレクション、`getattr`/`eval` の類、動的 import、
   DI コンテナ、プラグイン登録、ルーティング表、イベント名、ジョブ名
2. **コード以外からの参照** — 設定ファイル、環境変数、CI 定義、コンテナ定義、
   テンプレート、SQL、マイグレーション、i18n キー、ドキュメント、スクリプト
3. **シリアライズ境界** — DB のテーブル・カラム・ビュー・制約、API のレスポンス、
   保存済みデータ、キャッシュのキー、メッセージのスキーマ。
   フィールドを消すと過去のデータが読めなくなる
4. **ビルド時** — コード生成の入力、マクロ、条件コンパイル、ビルドフラグ、
   OS やフィーチャによる条件付きコンパイル
5. **外部の利用者** — 公開 API、エクスポートされた型、他リポジトリ、
   ドキュメントやサンプルに載っている名前
6. **副作用のための存在** — import しただけで登録が走るもの、初期化、計測、監査、
   ロック取得。返り値が使われていなくても必要なことがある
7. **履歴** — `git log` で、いつ入ったか、最近まで使われていたか。
   直近で足されたばかりなら、これから使う予定のものかもしれない
8. **仕様上の必要** — エラー処理、リカバリ経路、異常系、rollback 用のフラグ、
   互換性のための分岐は、平常時に到達しないだけで不要ではない

**テストからのみ使われている場合**は「使われている」ではなく、
**「テストごと見直す」**と報告してください。プロダクトコードで死んでいる合図です。

## 種類 2「寄せる」(重複・過剰な間接化)

こちらは**両方とも使われています**。使われていることは反証になりません。
問うのは「**片方に寄せると壊れるか**」です。次を当たってください。

1. **本当に同じか** — エッジケース、エラー時の挙動、境界値、型、精度、
   ログやメトリクスの差。一見同じで挙動が違うものを統合するのが一番危ない
2. **意図的に分けてあるか** — 所有者が違う、デプロイ単位が違う、変更の理由が違う、
   一方だけが外部仕様に縛られている
3. **その間接化が支えているもの** — テストでの差し替え、依存の逆転、
   モックの境界、権限や計測を挟む場所、将来ではなく**今**別実装が入る余地
4. **性能上の理由** — インライン化、コピーによるキャッシュ局所性、
   ホットパスでの分岐削減
5. **寄せた先の負担** — 統合後の関数が引数やフラグで肥大化しないか。
   引数で分岐する 1 つの関数より、2 つの関数の方が読みやすいことがある

## 報告 (標準出力に日本語で)

候補ごとに 1 ブロック。**判定を必ず 3 つのどれかにする。**

```
### 候補 <番号> : <対象>  [消す / 寄せる]
判定  : 反証された / 反証できなかった / 判断保留
証拠  : <見つけたものの場所と、探したコマンド。
        反証できなかった場合は、当たった項目と探索範囲>
補足  : <消すなら一緒に消すべきもの、先に確認すべきこと、外部への影響。
        寄せるなら、どちらに寄せるべきかと、その理由>
```

- **反証された**: 種類 1 のうち利用の有無で決まるものなら、使われている証拠がある。
  利用の有無で決まらないものなら、上の表の「反証されるのは」に当たった。
  種類 2 なら、寄せると壊れる理由がある
- **反証できなかった**: 該当する項目をすべて当たって、何も見つからなかった
- **判断保留**: 確かめる手段がない、あるいは確かめきれなかった。
  どの項目を確かめられなかったかを必ず書く

最後に、**リスト全体を通しての所見**を短く。特に、まとめて消すと壊れる組合せ、
消す順番に依存があるものを指摘してください。

自分が確かめていないことを「反証できなかった」に入れないこと。迷ったら判断保留にすること。
