# writeup — コードを読まない相手への説明文書を書く

対象はコードベース、サブシステム、実験、調査結果のいずれでもよい。読み手は、コードを読まない
(あるいは読む前の) 人間 — 新しくチームに入る人、他チーム、レビュアー、上長、指導教員など。

## 登場人物

| 呼び方 | 誰か |
| --- | --- |
| **実行者** | この手順を回すあなた。埋める・仕分ける・採否を決める・最後に自分で確かめる |
| **執筆エージェント** | 雛形 01 / 04 を渡された `codex exec`。文書を書く |
| **検証エージェント** | 雛形 02 / 03 / 05 を渡された `codex exec`。確かめる・批評する。文書は書かない |
| **依頼者** | この文書を求めた人 |

## 使う前に決める 3 つ

### 1. 根拠があるか

主張の種類ごとに根拠が違う。**全部が要るわけではない**。

| 文書に書く主張 | 根拠 | その根拠がないとき |
| --- | --- | --- |
| 実装・構造・依存 | コード | 使わない (書けない) |
| 挙動・数値・性能 | 実行結果、ログ、テスト出力 | コードから読める範囲に限定し、残りは「未確認」として書く |
| 目的・経緯・設計意図 | 一次資料 = 当時の判断が残っている記録 (設計文書、issue、PR、コミットメッセージ) | 「なぜそうなっているかは不明」と書く。コードから意図を推測して断定しない |
| 運用上の契約、本番環境で今どうなっているか | 実環境の記録 | この手順では扱わない (手元で再現して得た実行結果は、上の「挙動・数値」として扱える) |

**中心的な問いへの答えを、その主張の種類に対応する根拠から確認できないなら使わない**。要求仕様、
将来の設計提案、数学的な正当性の証明、組織的・人的要因を扱うポストモーテム、規格適合の説明が
これにあたる。手順そのものを説明する文書 (この skill 自身を含む) では、CLI の仕様、ファイル間の
対応、コマンドの実際の挙動までは 02 で確かめられる。確かめられないのは、その手順がなぜそう
設計されているかと、実際に良い結果を生むかどうか。

### 2. どこまで回すか

| モード | 使うとき | 走らせる手順 | 事実の独立確認 |
| --- | --- | --- | --- |
| 軽量 | 間違っても口頭で訂正できる。引き継ぎのメモ、数ファイルの説明 | 1 → 2 (03 だけ) → 実行者が直す | 実行者が全件 (02 が無いので、最後の高リスクだけの照合では足りない) |
| 標準 | 他人がこれを見て作業する。サブシステム説明、設計説明 | 1 → 2 → 3 → 4 → 実行者が確認 | 02 + 実行者 |
| 厳格 | 間違うと判断を誤らせる。計測・実験の報告、事故報告、外に出す文書 | 1 → 2 → 3 → 4 → 5 → 実行者が確認 | 02 + 実行者 (05 は読者としての確認で、事実は見ない) |

手順 3 は 02 の報告を入力にするので、軽量モードでは走らせない。

判断はファイル数ではなく**間違えたときの影響**で決める。

大きなコードベースの「全体像」を 1 本で書かせない。**先に対象を割る**。割る境界は、読み手の目的が
変わるところ、実行経路が分かれるところ、責任の持ち主が変わるところ。全体像が要るなら、割った文書を
書いてから、それらを束ねる短い文書を最後に書く。

### 3. 読み手が何のために読むのか

**読み終えた読み手が、何を判断できて、何をできるようになるか**を先に決める。ここが決まっていないと、
どの深さまで書くかが誰にも決められない。

## 前提

中間ファイルは一時作業領域に置く。以下 `$W` を作業ディレクトリ、`$T` を対象文書を置く
ディレクトリとする。パスは自分の環境のものに置き換える。

断片ごとにシェルが変わる環境 (Claude Code の Bash など) では、**変数は次の断片に引き継がれない**。
以下 3 行を**各断片の先頭で書き直す**。`$W` が空のまま実行すると、`/01.md` のように
ルート直下を触ろうとする。

```sh
W="<scratchpad>/writeup"
S="$HOME/.claude/skills/writeup/prompts"   # この skill の置き場所
T="<対象リポジトリ、または文書を置くディレクトリ>"
```

最初に 1 回だけ:

```sh
command -v codex >/dev/null || { echo "codex CLI が要る"; exit 1; }
mkdir -p "$W" || exit 1
test -z "$(ls -A "$W")" || { echo "$W に前回の残りがある。別の名前にする"; exit 1; }
mkdir -p "$W/observations" || exit 1
```

- **プロンプト内のパスはすべて絶対パス**にする。工程ごとに `-C` で渡す作業ルートが違う
- 書き込みを縛るのは `--sandbox` と、`-C` / `--add-dir` で与えた範囲。
  **プロンプトの禁止文よりこの指定で縛る**。ただし実際に書ける範囲は codex 側の設定にも依るので、
  対象を「書かれては困る場所」に置いたまま安心しない
- 変数はすべて引用する
- **`$W` と、文書の出力先を別の場所にする**。同じ場所に置くと、下の「02 は対象を書き換えられない」
  が成り立たなくなる

## 各工程の入出力

| 工程 | 読む | 書く | 標準出力に出る |
| --- | --- | --- | --- |
| 01 執筆 | コード、実行結果、一次資料 | 説明本文 (末尾に食い違いを仮置き) | 書けなかったこと、迷った点 |
| 02 事実検証 | 文書、コード、実行結果 | `$W` の中だけ (自分の確認コード) | 誤り / 裏が取れない / 誤解を招く / 確認した主張の一覧 |
| 03 編集批評 | まず文書だけ。読後の評価を固めてから、確認が要る箇所だけコード | なし | 理解できない箇所 / 不要な文 / 構成 / 文章表現と表記ゆれ / 全体評価 |
| 04 書き直し | 文書、コード、実行結果、実行者が仕分けた指摘 | 説明本文、食い違いメモ | 変更点、裏が取れていない点 |
| 05 最終読み | 文書 | なし | 理解できない箇所 / 不要な文 / 内部矛盾 |

## 原則

1. **根拠の切り分け** — 上の表のとおり。README・wiki・過去のメモ・コード内コメントは
   **主張であって根拠ではない**。実装上の事実がコードと食い違ったらコードを正とする。
   設計意図が食い違ったらどちらも正としない。どちらの場合も、食い違いと、確認したコミット ID・
   資料の版と日付を記録する。
2. **雛形はそれぞれ別の `codex exec` で実行する**。
3. **独立した確認とは、別の `codex exec` が、前段の出力を根拠にせず自分で確かめること**。
   原稿そのものは確認の回数に数えない。04 が書き直しながら行う再確認も、
   誤りを持ち込まないための自衛であって独立した確認ではない。必要な回数はモード表のとおり。
4. **採否は実行者が決める**。基準は手順 4 の表。

## 手順

### 0. 下調べ (実行者)

雛形の `{{...}}` のうち、全工程で使い回す欄を確定させる。この段階では精読しない。

| 欄 | 例 |
| --- | --- |
| 対象と、何の説明か | 「認証まわりの引き継ぎ資料」 |
| 読み手が、読んだ後に判断・実行できるべきこと | 「認証エラーの一次切り分けを 1 人でできる」 |
| 答える中心的な問い | 「どこでトークンが検証され、失敗したらどう見えるか」 |
| 扱わない範囲 | 「認可のポリシー設計は別文書」 |
| コードの絶対パス | リポジトリ、主要モジュール。**広すぎるなら先に割る** |
| 実行結果の絶対パス | ログ、テスト出力、計測結果。なければ「なし」 |
| 動かし方 | `cd ~/proj && pytest -q`。動かせないなら「なし」。**手順 3 の安全条件を満たすものだけ渡す** |
| 一次資料の絶対パス | 設計文書、issue、コミット履歴。なければ「なし」 |
| 根拠にしない資料 | `~/proj/README.md`、wiki |
| 読み手と、その語彙 | 「このサービスは知らないが Web の一般知識はある新メンバー」 |
| 文書の書き手 (03 で使う) | 「前任者」「この skill を回している自分」 |
| 出力先 | 説明本文は `$T` の中。食い違いメモは `$T` か `$W` の中 |

**読み手の語彙と目的は必ず確認する**。分からなければ依頼者に聞く。
聞ける相手がいないなら、読み手と目的が決まらないまま始めない。

「なし」の欄は、その欄だけを雛形から消す。1 行に複数の欄があるので、欄を消して文が壊れるなら、
その文ごと書き直す。

実行結果も動かす手段もない対象では、挙動と数値の根拠がコードだけになる。02 からは数値と再集計に
関する記述をすべて消し、確認手段を「コードを読んで呼び出しとデータの流れを追う」に差し替える。
一次資料があるなら、目的と経緯はそちらで裏を取る (コミット履歴も一次資料に含む)。
一次資料も無いなら、目的と経緯は「不明」と書かせる。

### 1. 執筆 (既存文書を直すだけなら飛ばして 2 へ)

```sh
rm -f "$W/01.md"; cp "$S/01-draft.md" "$W/01.md" || exit 1   # → {{...}} を埋める。未使用の欄は消す
grep -q "{{" "$W/01.md" && { echo "未置換あり"; exit 1; }
rm -f "$W/01.report"
codex exec -C "$T" --add-dir "$W" --sandbox workspace-write --skip-git-repo-check \
  -o "$W/01.report" - < "$W/01.md" \
  && test -s "$W/01.report" || { echo "01 が失敗、または空"; exit 1; }
```

執筆エージェントは、報告だけ返して本文を書かないことがある。次に進む前に、
**出力先の本文を実行者が開いて、今回書かれたものだと確かめる** (既存文書を直す場合、
前の版がそのまま残っていても報告は返る)。書かれていなければ 01 をやり直す。

**`01.report` も実行者が読む。** ここに出る「コードから裏が取れず書けなかったこと」と
「判断に迷った点」は、**本文には現れない**。02 も文中の主張しか見ないので、
実行者が読まなければ誰も見ない。書けなかったことが中心的な問いに関わるなら、
根拠を足すか、対象を割り直すか、その範囲を「扱わない」に移すかを、02 に進む前に決める。

### 2. 検証

標準・厳格モード:

```sh
rm -f "$W/02.md" "$W/03.md"
cp "$S/02-factcheck.md" "$W/02.md" && cp "$S/03-edit.md" "$W/03.md" || exit 1   # → 埋める
grep -q "{{" "$W/02.md" "$W/03.md" && { echo "未置換あり"; exit 1; }
rm -f "$W/02.report" "$W/03.report"
codex exec -C "$W" --sandbox workspace-write --skip-git-repo-check -o "$W/02.report" - < "$W/02.md" &
p2=$!
codex exec -C "$W" --sandbox read-only      --skip-git-repo-check -o "$W/03.report" - < "$W/03.md" &
p3=$!
ng=0; for p in $p2 $p3; do wait "$p" || ng=1; done   # 引数なしの wait は失敗を返さない
test "$ng" = 0 -a -s "$W/02.report" -a -s "$W/03.report" || { echo "検証が失敗、または空"; exit 1; }
```

軽量モード (03 だけ):

```sh
rm -f "$W/03.md"; cp "$S/03-edit.md" "$W/03.md" || exit 1   # → 埋める
grep -q "{{" "$W/03.md" && { echo "未置換あり"; exit 1; }
rm -f "$W/03.report"
codex exec -C "$W" --sandbox read-only --skip-git-repo-check -o "$W/03.report" - < "$W/03.md" \
  && test -s "$W/03.report" || { echo "03 が失敗、または空"; exit 1; }
```

標準・厳格モードで 02 と 03 の指摘が食い違ったら、どちらも自動で採らない。事実に関わるものは
実行者が自分で照合して決め、書き方に関わるものは手順 0 で決めた読み手と目的を基準に決める。
決められなければ食い違いメモに残す。

### 3. 裏の取れない主張を、実行者が確かめる (標準・厳格モードだけ)

検証報告に「文書にはこう書いてあるが、コードにも実行結果にもその裏がない」が出たら、
テストを走らせる・その機能を実際に実行する・計測をやり直す、で確かめられないか考える。
確かめられる場合、次をすべて満たすときだけ実行する。

この安全条件は、**01 と 04 に「動かし方」として渡すコマンドにも同じように当てはめる**。
渡した先で実行されるのは実行者が実行するのと同じことなので、渡す前に満たすか確かめる。

- コマンドと、かかる時間の見当がつく
- 既存の成果物を上書きしない (出力先を新しい名前にする)
- 外部への送信・課金・破壊的操作がない
- 永続的な状態を変えない (DB 更新、キュー投入、常駐プロセス、ポート占有)
- 認証情報や秘密情報を読み出さない

一つでも判断がつかないなら、依頼者に聞く。聞ける相手がいないなら実行しない。

実行したら出力を `$W/observations/<日付>-<何の記録か>.log` に保存し、手順 4 で
**その絶対パスと、再現に要るもの (コマンド、作業ディレクトリ、終了コード)** を渡す。
実行しないなら、**裏が取れないまま**として `$W/notes.md` に書き留め、手順 4 で
04 の「未確認のまま残った主張」の欄に書き写す。

### 4. 書き直し

```sh
rm -f "$W/04.md"; cp "$S/04-rewrite.md" "$W/04.md" || exit 1   # → 埋める
grep -q "{{" "$W/04.md" && { echo "未置換あり"; exit 1; }
rm -f "$W/04.report"
codex exec -C "$T" --add-dir "$W" --sandbox workspace-write --skip-git-repo-check \
  -o "$W/04.report" - < "$W/04.md" \
  && test -s "$W/04.report" || { echo "04 が失敗、または空"; exit 1; }
```

02 と 03 の報告を、この表で仕分けてから 04 の欄に書き写す。**報告全文を渡さない**。

| 指摘の種類 | 扱い |
| --- | --- |
| 事実の誤り・誤解を招く記述 | 必ず直す |
| 裏が取れない主張 | 結論に不要なら削除、判断に必要なら「未確認」として限界に書く。どちらでも食い違いメモには残す |
| 削除候補、全体を貫く記述 | **残す側に理由が要る。** 誰がどの場面で困るかを言えないなら消す |
| 前提に寄りかかった言い回し | 前提を書き足すのではなく、前提を要らなくする言い方に直す |
| 読みやすさ・構成の提案 | 読み手と目的に照らして選ぶ。落としてよい |
| 用語の言い換え提案 | 読み手の語彙が基準。手順 0 で決めたものを優先する |

採用しなかった事実関係の指摘は、理由を食い違いメモに残す。

01 と同じく、04 のあとも**本文と食い違いメモを実行者が開いて、今回の指摘が反映されているか**を
確かめる。04 が報告だけ返して書かないことがある。
**`04.report` も読む。** 「裏が取れていない点」は本文に残らないことがある。

### 5. 最終読み (厳格モードだけ)

```sh
rm -f "$W/05.md"; cp "$S/05-final.md" "$W/05.md" || exit 1   # → 埋める
grep -q "{{" "$W/05.md" && { echo "未置換あり"; exit 1; }
rm -f "$W/05.report"
codex exec -C "$W" --sandbox read-only --skip-git-repo-check -o "$W/05.report" - < "$W/05.md" \
  && test -s "$W/05.report" || { echo "05 が失敗、または空"; exit 1; }
```

**05 には、こちらが危ないと思っている箇所を渡さない。** 渡すと、自然に読んで詰まった場所を
報告する独立した読者が、こちらの見立てを確かめる係に変わる。
書き直した節や一括置換した用語が心配なら、**05 の報告を受け取った後に**、
別途その箇所だけを聞く。

指摘が出たら、事実に関わるものと節をまたぐものは 04 をもう一度走らせて直し、05 も走らせ直す。
一文で直る指摘は実行者が直し、その箇所だけ読み返す。

### 最後に実行者が確かめる

02 が全件を確認するのに対し、ここでは**結論に関わる高リスクの主張だけ**を自分で照合する。
対象は、結論を直接支える主張、要旨に書いた数値、比率の分子と分母、「必ず〜する」「〜しない」の類。
既存の集計・レポート処理の出力ではなく、生のデータやコードから確認する。

## 成果物

| ファイル | 中身 | 読み手 |
| --- | --- | --- |
| 説明本文 | 結論と根拠だけ。結論と、読み手が次に取れる行動で終える | その文書の読み手 |
| 食い違いメモ | ドキュメントとコードの不一致、裏の取れなかった主張、環境の制約、採用しなかった事実関係の指摘 | 実行者と後任 |

01 は食い違いを本文末に書くので、外して別ファイルにするのは 04。04 を走らせない軽量モードでは、
実行者が自分で外して依頼者への報告に回す。

## 用語

読み手の語彙に合わせる。その分野で英語のまま通じる語、コードとログに出てくる語は、そのまま使う。
一般的な日本語にない逐語訳は避ける。手順 4 で**対応表を書いて渡す**と一度で揃う。1 語ずつ直させない。

別の言語で書かせるなら、雛形の「日本語の Markdown」をその言語に置き換える。

## 落とし穴

- **codex のサンドボックスの制約を、対象の限界と書かせない**。子プロセスを作れずに落ちたテストを
  「対象の制約」として書いてくることがある。環境起因の失敗は実行者が再実行して確かめる。
- **実行者が渡した例文の用語ミスがそのまま本文に入る**。渡す具体例は先に確認する。
- **「〜だから〜になる」の前提が抜けた断定**は指摘されやすい。条件付きの言い方に直す。
- **「有効だった」「速くなった」式の評価**は比較対象がなければ書けない。評価を落としたうえで、
  比較していないことを限界に書く。
- **検証エージェントは、渡された資料のうち一番「検算しやすいもの」に引き寄せられる**。
  対象文書そのものより過去の記録に数字が多いと、そちらを検証して報告してくる。
  02 に渡す資料は、対象文書の主張を裏づけるものだけに絞る。
