# 具体例：why の強さと根拠

必要な例だけ参照する。以下は本パッケージのために作成した架空の例であり、実在の不具合・issue・計測結果を報告するものではない。各例の前提が実際の依頼やコードから確認できる場合にだけ、同種の理由を使う。

## 1. 不具合修正：差分の説明から、問題の説明へ

前提：仕様は「現在時刻が expiresAt 以上なら期限切れ」。現状は境界時刻を有効と扱い、変更は `>` を `>=` にするもの。対象の回帰テストも同梱する。

弱い文案：

```text
fix(cache): 比較演算子を変更

バグを修正して信頼性を向上するため。
```

改善した文案：

```text
fix(cache): 期限到達時のエントリを無効にする

現在時刻が expiresAt と一致すると期限切れの値を返してしまう。
期限に到達した時点で無効にする仕様に合わせ、境界時刻も
期限切れとして扱う。
```

比較演算子の変更は how。期限切れの値を返すことと仕様の不一致が why。同梱テストの存在だけを理由に `test` に変えない。「テストを追加した」と「テストに合格した」は別の主張である。

## 2. リファクタリング：抽象的な保守性から、具体的な制約へ

前提：ログインとパスワード再設定に同じ期限判定があり、挙動を変えず共通化する。目的は、今後の判定修正時に片方だけを更新することを避けること。

```text
refactor(auth): 期限判定を共通化する

ログインとパスワード再設定に同じ期限判定があり、判定の修正時に
両方を変更する必要がある。片方だけを更新することを避けるため、
同じ判定関数を共有し、現在の挙動は維持する。
```

「保守性向上」で止めず、何を維持する際のどんなリスクを減らすのかを書く。共通化と同時に挙動を直す場合、その修正を単なる refactor に隠さない。

## 3. 小さな文書修正：本文は必要だが、一文で足りる

前提：README の環境変数名は `CACHE_TLL`、実装で受け付ける名前は `CACHE_TTL`。修正は README のみ。

```text
docs(readme): キャッシュ設定の変数名を訂正する

記載どおりの変数名では実装が設定を読み取らないため、実際に受け付ける CACHE_TTL に合わせる。
```

架空の利用者被害、重大障害、性能劣化を足さない。単なるスペル修正なら、「用語集の表記と一致させる」など確認できる目的の一文でよい。

## 4. 破壊的変更：理由と移行方法は別々に必要

前提：秒単位の整数を受け取る `CACHE_TTL` を、単位を明示する `CACHE_TTL_SECONDS` に置換する設計が承認されている。旧名の互換エイリアスは残さない。単位は変わらない。

```text
feat(config)!: キャッシュ期限の環境変数名に秒単位を明示する

CACHE_TTL という名前では値の時間単位が分からないため、
秒を表す名前に統一する。値の単位は変更せず、旧名の受付は終了する。

BREAKING CHANGE: CACHE_TTL は読み取られなくなる。
  デプロイ設定を CACHE_TTL_SECONDS に変更する。
  秒単位の整数値はそのまま移せる。
```

`!` と footer の併記はこの例の選択であり、Conventional Commits は常に両方を要求するわけではない。旧名も受け付ける実装なら、同じ破壊的変更の説明は使えない。

## 5. 理由が不明：数値から物語を作らない

前提：取得できた情報は、定数の timeout が 5 から 30 に変わった差分だけ。単位、外部制約、依頼理由を確認できない。

完成扱いにしてはいけない文案：

```text
fix(network): タイムアウトを延長する

本番環境の遅延で失敗していたリクエストを成功させるため。
```

この前提で返すべき不足の説明の例：

> 5 から 30 への変更は確認できますが、変更理由と値の単位は確認できません。新しい値を必要とする制約・要求が必要です。実際の障害があったとは断定せず、コミットは実行しません。

一方、関連テストが根拠ある境界条件を示している場合まで、理由はコードから一切分からないと決めつけない。

## 6. issue 参照：番号だけでは理由にならない

前提：実在する対象リポジトリの issue #123 を確認済みで、「空の検索条件で全件取得すると意図しない大規模走査になるため、空条件を拒否する」と記載されている。変更は入力検証を追加するもの。

```text
fix(search): 空の検索条件を拒否する

空の検索条件が全件取得として扱われ、意図しない大規模走査を
発生させるため、検索前に空条件を拒否する。

Refs: #123
```

これは架空の fixture 番号。実際の文案に流用しない。理由は本文にあり、参照は追跡のために追加されている。

## 7. コミットの境界：ファイル種別ではなく意図でまとめる

入力が「期限判定の修正、その回帰テスト、修正した仕様の説明」であれば、一つの `fix` として扱える。
入力が「期限判定の修正と、無関係な CI のキャッシュ設定変更」であれば、独立した二つの意図として分ける。

後者がすでに index に混在していても、他者の staged 変更を勝手に外して分割しない。必要な整理の範囲を確認する。
メッセージだけの依頼であれば、分割案を返すだけで index を変更しない。
